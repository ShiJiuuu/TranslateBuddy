# Dify 文档翻译插件方案 v2（TranslateBuddy）

> **v2 依据你的 7 条答复修订**：Docker 自托管 · 先中英 · **可读优先** · 只要译文 · **100+ 页** · 术语表 + 基础 QA · 插件 + 工作流 DSL。
> 另按补充要求调整：`.doc → .docx`、`.xls → .xlsx` **不回转**；上传上限 **500 MB**；工作流总时长 **7200 s**。

| # | v1 | v2 | 为什么 |
|---|---|---|---|
| 1 | PDF 把译文塞进原 bbox，放不下就缩字号 | **列内重排 + 续页**，字号优先 | 你选"可读"；塞框会让中文/英文都变蚂蚁字 |

## 1. 需求与约束（v2 已确认）

| 项 | 结论 |
|---|---|
| 部署 | Dify 自托管，Docker Compose |
| 语言 | 中↔英，架构保留多语扩展位（字体、断行按目标语言选） |
| 保真取向 | **可读优先**：允许分页变化、允许页数变多，不接受缩成蚂蚁字 |
| 译文形态 | 只输出译文 |
| 规模 | 常规 100+ 页，设计目标 **300 页 / 500 MB** |
| 格式 | pdf→pdf、docx→docx、xlsx→xlsx；**doc→docx、xls→xlsx** |
| 质量 | 术语表强制统一 + 基础 QA（数字/占位符/空译/长度） |
| 交付 | 插件包 + 可一键导入的 Dify 工作流 DSL |

**运行环境约束（必须改，否则上面全是空话）**：

| 变量 | 默认 | 目标 | 位置 |
|---|---|---|---|
| `UPLOAD_FILE_SIZE_LIMIT` | 15（MB） | **500** | api |
| `NGINX_CLIENT_MAX_BODY_SIZE` | 100M | **500M** | nginx |
| `PLUGIN_MAX_FILE_SIZE` | 50 MB | **600 MB** | api：**插件产出文件**的上限（源码注释：plugin-generated files）；留出字体嵌入/加页的余量 |
| `PLUGIN_MAX_EXECUTION_TIMEOUT` | 600 s | **1800 s** | plugin_daemon：单次插件调用 |
| `WORKFLOW_MAX_EXECUTION_TIME` | 3600 s | **7200 s** | api |
| `APP_MAX_EXECUTION_TIME` | 3600 s | **7200 s** | api |
| `NGINX_PROXY_READ_TIMEOUT` | 3600s | **7200s** | nginx（Chatflow 长连接） |

> 注意 `PLUGIN_MAX_FILE_SIZE` 管的是**输出**，不是输入。500 MB 的译文文件不调这个，Dify 会直接拒收——这是最容易漏的一条。

## 2. 总体架构

一个插件、四个动作、两个使用姿势：

```
                        ┌─────────────── Dify 工作流 ───────────────┐
 上传文件 ──▶ inspect_document   （预检：页数/段数/扫描件/预估耗时与成本）
                        │
              ┌─────────┴──────────┐
              │                    │
         ≤50 页小文件         100+ 页大文件
              │                    │
    translate_document      parse_document  ──▶ job_id + shard 计划
    （一体化，内部作业）            │
              │             迭代节点 × translate_shard（LLM）
              │                    │
              │             render_document(job_id)
              └─────────┬──────────┘
                        ▼
                 同格式译文文件（blob）
```

- **一体化**：一个节点跑完，适合 ≤50 页。超限直接返回 `E_TOO_LARGE` 并给分片建议，不静默超时。
- **分片**：100+ 页走这条路。每个分片 60 段 / ≈8000 字符，单次调用 15–30 s，天然避开超时，还能断点续跑。
- 两套共用同一份 IR 与回写引擎。

## 3. IR 与作业模型

```python
@dataclass
class Segment:
    id: str          # "doc/p12/r3" / "sheet1!B4" / "pdf/p2/b7"
    text: str
    path: tuple      # 回写定位
    kind: str        # paragraph | cell | header | footer | note | pdf_block
    meta: dict       # 字体/字号/颜色/bbox/对齐（PDF 与 docx 共用）
    ctx: dict        # 前后段、章节标题、表头
    translatable: bool
    translated: str | None
    status: str      # pending | done | failed | skipped

@dataclass
class Job:
    job_id: str          # uuid4
    owner: str           # 由 session.user_id 派生，隔离用
    source_format: str   # pdf | docx | xlsx
    out_format: str      # 同 source，doc/xls 已升级
    source_file: Path    # 临时文件，不读进内存
    segments: list[Segment]
    shards: list[list[str]]   # 每个分片的 segment id
    status: dict              # 各分片进度
    created_at / ttl
```

**存储布局**（落在 plugin_daemon 的 `/app/storage/jobs/`，需挂卷）：

```
/app/storage/jobs/<job_id>/
├── source.pdf          # 原始文件（流式落盘，不整块进内存）
├── segments.json       # 分段（含 path/meta/ctx）
├── shards.json         # 分片计划
├── shard_000.json ...  # 分片译文（含 hash、状态、用量）
└── result.docx         # 回写产物
```

- 分片结果**原子写**（tmp + rename），支持并发。
- TTL 24 h，每小时清理；`job_id` 为 uuid4，按 owner 校验，防止越权读取别人的文档。
- 若 daemon 多副本：必须共享卷，或把作业目录换成 Redis/S3（预留接口）。
- 大文件**永远走文件路径**：`File.blob` 会把整个文件读进内存，500 MB 会直接 OOM。用 `file.url` + `httpx.stream` 落盘。

## 4. 格式策略

### 4.0 保真等级（不变）

| 等级 | 含义 | 本项目 |
|---|---|---|
| L0 | 重建文档 | 不做 |
| L1 | 读入模型再保存 | doc/xls 转换时被动经过 |
| **L2** | 只改文字节点，其余字节不动 | docx / xlsx / pdf 的目标 |

### 4.1 DOCX —— L2

- zip 级修改：`document.xml` / `header*.xml` / `footer*.xml` / `footnotes.xml` / `endnotes.xml` / `comments.xml`，其余条目**流式拷贝**（`shutil.copyfileobj`，不整块读，500 MB 也不爆）。
- run 先按 `rPr` 签名合并成"格式片段"，再翻译；没被识别为文字的节点（`instrText`、`fldChar`、`del/ins`、`drawing`、书签、批注引用）一律跳过。
- 段内多格式用 `⟦b⟧…⟦/b⟧` 标签，校验失败降级"整段单格式"。
- 覆盖：表格、文本框、页眉页脚、脚注尾注、批注、内容控件。
- 域（目录/页码）不重算，提示用户 F9 更新。

### 4.2 XLSX —— L2

- 直接改 `xl/sharedStrings.xml` / `inlineStr`，其余 zip 条目原样。
- 大文件（>50 MB）的字符串表用 `iterparse` 流式重建，避免内存翻倍。
- 公式、数字格式、合并区、条件格式、图表、数据验证天然不动。
- 公式里的字符串常量单独扫描告警（`=IF(A1="Revenue",…)` 会失配）。
- 工作表名/定义名称默认不译；列宽自适应默认关闭。

### 4.3 PDF —— 可读优先，要重排（本方案最大工作量）

**不再把译文硬塞进原框**，改成"列内重排"：

1. **版面重建**：按 x 聚类识别列，列内 block 按 y 排序；图片/矢量块作为障碍物；页眉页脚单独识别。
2. **先删后排**：整页用 `redact` 清掉原文（`images=NONE, graphics=NONE` 保留画面），再按列重排。
3. **游标排版**：列顶开始，逐块 `insert_htmlbox`，**保持原字号与颜色**，宽度=列宽，高度=到下一个障碍/页底；用返回的 `spare_height` 反推实际占用高度，推进游标。
4. **放不下就往下推**：后续块整体下移；推到页底还不够 → **在当前页后插入续页**（同尺寸，复制页眉页脚），剩余内容继续排；单块高过一页时按句切分、跨页续排。阅读顺序不乱，代价是页数变多、原页码错位。
5. **仅当连一行都放不下**才缩字号（下限 0.85），再不行才标记"未译/截断"。
6. **不重排的降级区**：表格、旋转文本、块与块重叠的复杂版式 → 回落到"原框内缩排"（fit 模式），并在报告里标注原因。
7. **行内样式**：同一 block 内不同 span 的粗/斜/颜色映射成 `<b>/<i>/<span style>`，交给 htmlbox 渲染。

**取舍（要先说清楚）**：

- 重排会把"版式 100% 一致"换成"读得舒服"，页数可能 +10%~30%（英译中通常变短，中译英通常变长）。
- 插入续页后原页脚页码会错位——可选"重排页脚纯数字页码"，默认关。
- 表格不参与重排，只在格内换行，必要时行高增长。

**一期不做**：扫描件/OCR、竖排、艺术字、表单域、数字签名（redact 会让签名失效，需提示）。

### 4.4 DOC / XLS —— 单向升级

```
doc  ──LibreOffice──▶ docx ──L2 翻译──▶ 交付 .docx
xls  ──LibreOffice──▶ xlsx ──L2 翻译──▶ 交付 .xlsx
```

- 输出文件名显式体现：`合同.doc` → `合同.zh.docx`，并在返回的 text 里说明"已升级为 docx"。
- 仍需要 LibreOffice：按 7.2 的 A（换 daemon 镜像）或 B（旁挂转换容器）；不装则这两个扩展名直接报 `E_NO_CONVERTER`，不静默失败。
- 转换有版式漂移（复杂表格、艺术字、图表），要在 UI 提示。

## 5. 大文档工程（100+ 页 / 500 MB）

### 5.1 预算（300 页为例）

| 指标 | 估算 | 说明 |
|---|---|---|
| 段数 | ~4,500 | 15 段/页 |
| 字符 | ~60 万（英） | 130 字符/段 |
| token | 输入 ~20 万 / 输出 ~30 万 | 中英 token 比按 1:1.5 估 |
| LLM 调用 | ~330 次 | 1,800 字符/批 |
| 分片 | ~75 个（60 段/片） | |
| 墙钟 | 8–15 min（并发 4） | 单批 3–5 s，含重试 |
| 成本 | 按模型单价 × 50 万 token 估 | `inspect_document` 会给预估 |

### 5.2 关键机制

- **分片幂等**：分片结果带 `hash(源文本 + 目标语言 + 模型 + 提示词版本)`，命中即跳过 → 重跑工作流不重复花钱，中断可续。
- **重试分层**：单批 429/超时 → 退避重试；单分片失败 → 只重跑该片；整片失败 → 保留原文并计入 `failed_segments`。
- **并发**：分片内部 4，工作流迭代并行 2–4，总并发 ≤ 12（可配），按 provider 限流调。
- **进度**：每次工具调用返回一行 `shard 12/75 done · 3,240/4,500 段 · 18.2 万 token`，直接在 Dify 日志里可见。
- **内存**：源文件只在磁盘；docx/xlsx 按条目流式；PDF 按页处理，每页处理完即释放。
- **输出上限**：接近 `PLUGIN_MAX_FILE_SIZE` 时提前报错，而不是传到一半被拒。
- **失败不产出半个文件**：`render_document` 先写临时文件，校验（可打开、页数、段数）通过后才返回 blob。

### 5.3 为什么按"段"分片而不是按"页"

页密度差异能到 10 倍（一页表格 vs 一页正文）。按字符/token 切，单片耗时稳定，超时风险可控。

## 6. LLM 协作协议

- **批量**：单批输入 ≤ 2000 token，带文档标题、章节标题、前后各一句上下文、**相关术语子集**（不是全表）。
- **结构化输出**：`{"id": "译文"}`；模型不支持 JSON 模式就解析 + 修复；`id` 缺失/多余视为失败并重试。
- **术语**：CSV（`source,target,case_sensitive`）命中后先用 `⟦T3⟧` 占位，翻完还原——比 prompt 叮嘱可靠。
- **QA**：空译 / 与原文相同 / 数字或单位缺失 / 占位符不匹配 / 标签不平衡 / 长度比 >3 或 <0.3 / 目标语言字符占比异常。结果进 `json`，`text` 给一句人话摘要。
- **去重**：同 hash 文本只翻一次（同一文档里重复的表头、免责声明很常见）。
- **温度** 0.1–0.3；`max_tokens` 按批估算，避免截断。

## 7. 部署：只动 Dify 已有的东西

### 7.0 先把关系理清：插件不是 Docker 镜像

```
docker compose up 之后（Dify 自己的容器）：

  nginx ──▶ api / worker ──▶ plugin_daemon ──spawn──▶ 插件代码（独立 venv）
                                   ▲
                                   └── 你上传的 .difypkg 就装在这里跑
```

- 插件产物是一个 **`.difypkg`（zip 包）**，在 Dify 后台「插件 → 安装 → 本地包」上传，**不构建、不运行任何新容器**。
- 插件的 Python 依赖（pymupdf、openpyxl…）由 plugin_daemon 在安装时用 pip 装进独立 venv；内网环境需要设 `PIP_MIRROR_URL`。
- 唯一可能动到"系统层"的是 **LibreOffice**（`.doc/.xls` 转换），它是操作系统包，装不进 venv——所以 7.2 才需要讨论，而且**只有这两个老格式需要**。

也就是说：`.doc/.xls` 之外的 90% 功能，你只需要改 `.env` 里几行 + `docker compose up -d`。

### 7.1 改 7 个环境变量（`dify/docker/.env`）

| 变量 | 谁读它 | 默认 → 目标 | 不改进会怎样 |
|---|---|---|---|
| `UPLOAD_FILE_SIZE_LIMIT` | api | 15 → **500**（MB） | 500 MB 文件上传直接被拒 |
| `NGINX_CLIENT_MAX_BODY_SIZE` | nginx | 100M → **500M** | 请求在 nginx 层就 413 |
| `PLUGIN_MAX_FILE_SIZE` | api | 50MB → **600MB** | 插件产出的译文文件被拒收 |
| `PLUGIN_MAX_EXECUTION_TIMEOUT` | plugin_daemon | 600 → **1800**（秒） | 大文件单次调用超时被杀 |
| `WORKFLOW_MAX_EXECUTION_TIME` | api | 3600 → **7200** | 100+ 页工作流跑一半被中断 |
| `APP_MAX_EXECUTION_TIME` | api | 3600 → **7200** | 同上（App 级） |
| `NGINX_PROXY_READ_TIMEOUT` | nginx | 3600s → **7200s** | Chatflow 长连接被掐断 |

```bash
cd dify/docker
vi .env            # 改上面 7 行
docker compose up -d
```

`docker compose up -d` 只会重建配置变了的 api / worker / nginx / plugin_daemon，数据都在 volumes 里，几分钟内完成。**不需要新建镜像。**

> 三条最容易被漏：`NGINX_CLIENT_MAX_BODY_SIZE`（只在 nginx 层生效，光改上传上限没用）、`PLUGIN_MAX_FILE_SIZE`（管**输出**不管输入）、`PLUGIN_MAX_EXECUTION_TIMEOUT`（管的是 daemon 侧单次调用）。

### 7.2 `.doc / .xls` 怎么办（可选，M4 再定）

LibreOffice 是系统包，三条路：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 换 daemon 镜像** | `FROM langgenius/dify-plugin-daemon:0.6.11-local` + `apt install libreoffice-writer libreoffice-calc`，compose 里改一行 `image:` | 镜像 +500 MB；所有插件共用这个镜像 |
| **B. 旁挂转换容器** | 单独起 `unoserver`/LibreOffice 容器，插件通过 HTTP 调 | 多一个服务，但不动 Dify 镜像 |
| **C. 先不支持** | 上传 `.doc/.xls` 时提示"请另存为 docx/xlsx"，返回明确错误码 | 0 改动，长尾用户要手动转一次 |

**建议：M0–M3 走 C**，先把 docx/xlsx/pdf 打穿；M4 再按实际需求切 A 或 B。多数文档源本来就以 docx/xlsx 为主。

### 7.3 资源

| 项 | 建议 |
|---|---|
| plugin_daemon 内存 | ≥ 4 GB（500 MB 文档 + 字体 + 可能的 LO） |
| 作业目录 | 默认已挂 `./volumes/plugin_daemon:/app/storage`，不用额外配 |
| 中文字体 | 随插件包带 Noto 子集（2–5 MB），**不用改镜像**；PDF 嵌入时再 subset |
| 转换安全 | 若启用 A/B：非 root、禁网、单文件 120 s 超时、文档隔离在 job 目录 |

## 8. 验证状态

**已验证（spike，fit 模式）**：

| 格式 | 结果 |
|---|---|
| docx | 13 段就地改；加粗/标红/斜体/表格/列表全保留 |
| xlsx | 6 单元格；合并区、填充色、`#,##0 "USD"`、`0.0%`、`=B4-B5` 全保留 |
| pdf | 7 个文本块在 bbox 内重排；表格线/页脚不变；字体子集化 3 KB → 30 KB（不子集化 12 MB） |

**PDF 重排骨架（第二轮 spike，原语已验证）**：

- 已验证：`Story.fit_height` 量出块在该列宽下需要的高度 → 游标排版 → 溢出自动插续页（26 段密集样本扩写 2 倍，自动加了 1 页，无重叠）。
- 暴露出来、M2 必须解决的 4 件事：
  1. **超长块必须拆**：单块高过一页时不能硬塞，要按句切分、跨页续排（否则文字会画到页面外）。
  2. **表格不能重排**：整块参与重排会把两列并成一列，表格要按单元格走 fit 模式。
  3. **硬换行要转软换行**：原 PDF 的换行是硬断行，直接保留会出现 "and" 独占一行的断句。
  4. **页眉页脚要锚定**：它们不能进正文流；另外文字重排后与保留的线条/图会错位，需要避让或降级。
- 结论：原语可用，工程量集中在"拆分 + 版面判断"。M2 仍是 8 人日，但风险从"未知"变成"已知问题清单"。

**仍未验证（M2–M4 要补）**：

1. 真实 PDF 样本（双栏论文、带表格合同）的重排质量——M2 第一周用 3 份真实文件验收，不达标就退回 fit 模式并调整承诺。
2. 500 MB 全链路（下载、解析、回写、上传）内存与耗时。
3. 真实 Word 文档里的复杂结构（内容控件、修订、文本框）。
4. LibreOffice 对真实 `.doc/.xls` 的转换保真度。

## 10. 风险

| 风险 | 影响 | 对策 |
|---|---|---|
| PDF 重排做不好 | 输出难看，方案核心受挫 | M2 先 spike 真实样本；保留 fit 模式兜底；表格/复杂版式不重排 |
| 500 MB 全链路爆内存 | 任务被杀 | 全程文件流式、临时目录、输出前预检大小；daemon 内存 ≥4 GB |
| `PLUGIN_MAX_FILE_SIZE` 漏配 | 大文件输出被静默拒绝 | 部署清单 + 启动自检（读 env 打印） |
| LibreOffice 转换失真/被攻击 | 版式漂移、安全 | 非 root、禁网、超时、单文件隔离；M4 用真实 .doc 验证 |
| 模型限流 | 大文档超时 | 并发可配、429 退避、分片重试 |
| 页码错位（插续页） | 用户困惑 | 报告里列出插入页；可选重排页脚数字 |
| 作业目录多副本不一致 | 分片丢失 | 单副本 or 共享卷；预留 Redis/S3 适配 |
